# 병렬 세션 운영

## 시작 전에 개발자에게 확인할 것 (한 번에 묻는다)
1. 목표와 끝나는 조건. "무엇이 나오면 끝인가"를 한 줄로.
2. 세션 수와 역할. 기본은 총괄 1 + 작업 세션 1~2. 세션을 늘릴 이유가 분명하지 않으면 늘리지 않는다.
3. 승인 범위. 다음 중 하나를 고르게 한다.
   - 제안까지만 (코드 변경 없음)
   - 작업 브랜치 커밋까지
   - 통합 브랜치(`dev`) 병합·push까지
   main으로 가는 PR과 병합은 어떤 경우에도 개발자에게 묻는다.

## 역할
- **총괄**: 요구사항 대조, 통합 브랜치 병합, 결과 판정. 통합 브랜치에 병합하는 세션은 총괄 하나뿐이다.
- **작업 세션**: 맡은 범위의 구현. 서로 같은 파일을 고치지 않도록 범위를 파일 단위로 나눠 준다.
- **리뷰·토론 세션**: 읽기만 한다. 결과만 보고하고 고칠지는 개발자가 정한다.

## 격리
- 코드를 쓰는 세션은 각자 worktree에서 일한다.
- 다른 세션이 쓰고 있는 체크아웃에서는 읽기 전용 세션도 띄우지 않는다. 리뷰 세션도 worktree에서 시작하거나, 커밋된 범위(`git diff A B`)만 보게 한다.
- `bash .claude/check.sh`는 잠금으로 한 번에 하나씩만 돈다. 기다리는 것이 정상이니 잠금 폴더를 직접 지우지 않는다.

## 지시문에 꼭 넣을 것
새 세션은 이 대화를 모른다. 지시문에 다음을 적는다.
- 목표와 끝나는 조건, 맡은 범위(파일·폴더), 건드리면 안 되는 것
- 승인 범위 (위에서 고른 것)
- "`CLAUDE.md`와 `.claude/team-rules.md`를 먼저 읽는다. 코드 변경은 `work-on-issue` 절차를 따른다."
- 보고 형식. 리뷰라면 `reviewer.md`의 판정 기준과 보고 형식을 그대로 쓰게 한다.
- 요구사항 원문은 붙여넣지 않고 `docs/requirements.md`를 읽게 한다.

## 소통
- 제안, 반박, 측정 결과는 공유 노트 폴더에 파일로 쓴다. 메시지에는 요약과 파일 이름만 보낸다.
- 다른 세션의 제안에 반대할 때는 측정값이나 재현 절차를 붙인다. 근거 없는 반대와 근거 없는 동의는 쓰지 않는다.
- 결정된 것은 총괄이 `docs/decisions/`에 한 파일로 남긴다.

## 끝낼 때 (총괄이 한다)
1. 세션별로 무엇이 통합 브랜치에 들어갔고 무엇이 안 들어갔는지 표로 보고한다.
2. 병합이 끝난 작업 브랜치를 지운다 (`git branch -d`. 병합 안 된 브랜치는 지우지 않고 목록으로 보고).
3. 끝난 worktree를 정리한다 (`git worktree remove`). 커밋 안 된 변경이 있으면 지우지 않고 보고한다.
4. `wip` 커밋이나 버려진 브랜치가 남았으면 어떻게 할지 개발자에게 묻는다.
5. 이번에 같은 지시를 반복해서 적은 것이 있으면 하네스 어디에 넣을지 개발자에게 제안한다.
